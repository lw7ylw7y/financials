# V1.1 User Stories & Acceptance Criteria — Web Dashboard

**Companion to:** investment_dashboard_requirements.md
**Scope:** Section 4 of the requirements doc (Indicator Digest Page, Ticker Dashboard)

**Note on scope change:** Ticker Email Alerts and Discount-Buy Thresholds (previously drafted as 4.2/4.3) were moved to the Backlog (Section 5 of the requirements doc) on 2026-09-12 and are not covered here. v1.1 is now two web pages: a read-only Indicator Digest Page (mirrors the v1 email) and the Ticker Dashboard.

---

## Epic: Indicator Digest Page

### Story 1 — On-Demand Indicator Page
**As** the investor, **I want** to open a web page and see the same macro-indicator content the digest email already sends me, **so that** I can check the current picture whenever I want instead of waiting for the next triggering email.

**Acceptance Criteria**
- [x] Page runs locally (e.g. `localhost`) — no public hosting, no domain, no login needed in this version (see Section 4.1 of the requirements doc; hosted/non-local is a later-version backlog item)
- [x] Page displays the same three content pieces as the digest email: the holistic AI interpretation + directional read (v1 Story 4), the indicator table grouped by category (v1 Story 5), and the next-release countdown (v1 Story 6)
- [x] AI-generated content is labeled as informational commentary, not personalized financial advice (same guardrail as the email)
- [x] If the AI interpretation is missing or failed on the most recent ingestion/live-pull run, the page still renders the table and countdown (same graceful-degradation behavior as the email)
- [x] The email digest (Section 3.1 of the requirements doc) continues to fire on its existing trigger, unchanged by the page's existence

### Story 1a — Background Live Check with In-Place Updates
**As** the investor, **I want** the page to load instantly from the last stored data and check for anything new in the background, updating only what's actually changed, **so that** I'm not staring at a spinner every time I open the page, and the AI isn't re-run for no reason when nothing's changed.

**Acceptance Criteria**
- [x] The page's initial load is built entirely from stored data — no live fetch blocks the response the reader first sees
- [x] After that initial render, the page checks for updates on its own (no user action required) — a live pull from FRED
- [x] If the check finds at least one indicator with a genuinely new value, the affected parts of the page (table, countdown, AI section) update in place, and the AI interpretation is re-run and shown
- [x] If the check finds nothing new, the page is left exactly as it was — no re-render, and **no AI call is made**, since there's nothing new to interpret
- [x] A check that finds new data writes it back to the shared historical data store (the same store the v1 email pipeline reads/writes), so the page and email stay consistent
- [x] If the background check fails outright (source API down, rate-limited, timeout, etc.), the page simply stays on the last stored data — same visible outcome as "checked, found nothing new"
- [x] The fallback/initial state includes the last successful AI summary/directional read, not just the indicator table — this requires persisting the most recent AI response (text + directional read + generated-at timestamp) to the data store, since v1 never saved it (v1 generated it fresh per email and discarded it after sending)
- [x] ~~The page shows a visible freshness label/timestamp~~ — dropped; found distracting in practice, and the background check's in-place content updates (see the "checking for updates" indicator below) are enough signal on their own
- [x] While the background check is in flight, the page shows a visible "checking for updates" indicator, so the reader isn't left wondering whether anything is happening; it disappears once the check settles, regardless of whether it found new data, found nothing new, or failed

## Epic: Ticker Dashboard

### Story 2 — Ticker Watchlist Configuration
**As** the investor, **I want** to maintain my ticker watchlist — and the groups it's organized into — in a simple config file, **so that** I can add, remove, or regroup tickers without touching application code.

**Acceptance Criteria**
- [x] Tickers are defined in a local JSON config file (per Section 7 of the requirements doc), grouped under group names that are themselves defined by the file — not a fixed list of categories hardcoded in the app
- [x] Initial watchlist matches the config draft: SPY, IVW, DGRO (stocks); VGIT, VGLT (bonds); VIGI, VYMI, EMB (international); FTEC + other sector ETFs (sector); MSFT, RELY + other trusted individual stocks (individual)
- [x] Adding or removing a ticker requires only editing the config file — no code change
- [x] Adding, removing, or renaming an entire group requires only editing the config file — no code change (this is the key difference from a v1.1 draft that had group names fixed in code)
- [x] An invalid or unrecognized ticker symbol in the config is skipped with a logged warning rather than breaking the whole dashboard

---

### Story 3 — Ticker Dashboard Page
**As** the investor, **I want** a web page showing my ticker watchlist grouped by asset type, **so that** I can review prices and trends across all my holdings in one place without logging into Fidelity.

**Acceptance Criteria**
- [x] Page runs locally (e.g. `localhost`) — no public hosting, no domain, no login needed in this version (same hosting decision as the Indicator Digest Page, Story 1)
- [x] Tickers are displayed grouped under headers matching the group names in the config file exactly — the page doesn't assume any fixed set of groups
- [x] ~~Each ticker card shows~~ Each ticker row (revised 2026-09-13 — a per-ticker card grid was hard to scan and switched to a table after initial use) shows: current price, 52-week range, 20-day moving average, 50-day moving average, and 200-day moving average
- [x] The 52-week range is shown as a green (near the low)→amber→red (near the high) gradient with a marker for the current price, plus the low/high as text, so the read doesn't depend on color alone
- [x] Each moving average shows both a color (green when price is above it, red when below — same convention as the AI directional badges) and a signed arrow+percentage, again not color-only
- [x] ~~and recent related news~~ — dropped 2026-09-13 after initial use, found it cluttered the table without adding enough value
- [x] Price and moving-average data is sourced from Finnhub and Yahoo Finance (see Section 6 of the requirements doc and Section 5's deviation note in the tech design — Finnhub's free tier turned out not to serve the historical closes moving averages need); the free-tier ~20-minute delay is acceptable and does not need to be surfaced as an error state
- [x] A ticker whose data fails to load (API error, rate limit), *and has never been successfully fetched before*, shows a visible per-row error state rather than breaking the rest of the dashboard
- [x] ~~Reloading the page re-fetches or re-reads current data rather than showing a stale snapshot from an earlier visit~~ — superseded by Story 5: the page's *initial* paint now intentionally shows the last cached snapshot instantly, with a background check re-fetching live moments later (same trade-off as the Indicator Digest Page, Story 1a) — a genuinely stale/never-updated dashboard was never the intent, and still isn't: the background check runs on every load

---

### Story 4 — Cross-Page Navigation
**As** the investor, **I want** to get from one v1.1 page to the other by clicking rather than typing a URL, **so that** the two pages feel like one dashboard rather than two disconnected tools.

**Acceptance Criteria**
- [x] Both the Indicator Digest Page and the Ticker Dashboard show a small nav linking to the other page
- [x] The nav visibly marks which page is currently active

---

### Story 5 — Ticker Dashboard: Instant Load with Background Refresh
**As** the investor, **I want** the Ticker Dashboard to load instantly from the last known prices and refresh live in the background, **so that** I'm not staring at a blank page while 11+ tickers' worth of Finnhub and Yahoo calls complete one by one.

**Acceptance Criteria**
- [x] The page's initial load is built entirely from a local snapshot cache (`data/tickers.json`, one entry per ticker) — no live fetch blocks the response the reader first sees, same pattern as the Indicator Digest Page (Story 1a)
- [x] A ticker with no cached snapshot yet (first-ever run, or just added to the config) renders as a "Loading…" placeholder row, not an error — it hasn't failed, it just hasn't been fetched yet
- [x] After the initial render, the page checks for live data on its own (no user action required); unlike the Indicator Digest Page there's no "skip if nothing changed" gate — Finnhub/Yahoo calls are cheap enough that every check re-fetches every ticker live
- [x] A successful live fetch for a ticker is persisted to the snapshot cache, so the *next* load has fresher stale data to fall back on
- [x] A ticker whose live fetch fails falls back to its last cached snapshot silently — no visible stale/live distinction (same call as the Indicator Digest Page's dropped Live/Saved badge); only a ticker with no cached snapshot *and* a failed live fetch shows the error state
- [x] While the background check is in flight, the page shows the same visible "checking for updates" indicator as the Indicator Digest Page; it disappears once the check settles either way

---

## Cross-Cutting Non-Functional Criteria (apply to all stories above)
- [x] Neither page requires user authentication
- [x] Both pages are usable on a desktop/web browser (per the v1.1 device scope — no mobile app)
- [x] A data-source outage (FRED, Finnhub, Yahoo) or missing data degrades gracefully (visible error/empty state) rather than crashing the page
