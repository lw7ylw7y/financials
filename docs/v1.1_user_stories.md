# V1.1 User Stories & Acceptance Criteria — Web Dashboard

**Companion to:** investment_dashboard_requirements.md
**Scope:** Section 4 of the requirements doc (Indicator Digest Page, Ticker Dashboard)

**Note on scope change:** Ticker Email Alerts and Discount-Buy Thresholds (previously drafted as 4.2/4.3) were moved to the Backlog (Section 5 of the requirements doc) on 2026-09-12 and are not covered here. v1.1 is now two web pages: a read-only Indicator Digest Page (mirrors the v1 email) and the Ticker Dashboard.

---

## Epic: Indicator Digest Page

### Story 1 — On-Demand Indicator Page
**As** the investor, **I want** to open a web page and see the same macro-indicator content the digest email already sends me, **so that** I can check the current picture whenever I want instead of waiting for the next triggering email.

**Acceptance Criteria**
- [ ] Page runs locally (e.g. `localhost`) — no public hosting, no domain, no login needed in this version (see Section 4.1 of the requirements doc; hosted/non-local is a later-version backlog item)
- [ ] Page displays the same three content pieces as the digest email: the holistic AI interpretation + directional read (v1 Story 4), the indicator table grouped by category (v1 Story 5), and the next-release countdown (v1 Story 6)
- [ ] AI-generated content is labeled as informational commentary, not personalized financial advice (same guardrail as the email)
- [ ] If the AI interpretation is missing or failed on the most recent ingestion/live-pull run, the page still renders the table and countdown (same graceful-degradation behavior as the email)
- [ ] The email digest (Section 3.1 of the requirements doc) continues to fire on its existing trigger, unchanged by the page's existence

### Story 1a — Background Live Check with In-Place Updates
**As** the investor, **I want** the page to load instantly from the last stored data and check for anything new in the background, updating only what's actually changed, **so that** I'm not staring at a spinner every time I open the page, and the AI isn't re-run for no reason when nothing's changed.

**Acceptance Criteria**
- [ ] The page's initial load is built entirely from stored data — no live fetch blocks the response the reader first sees
- [ ] After that initial render, the page checks for updates on its own (no user action required) — a live pull from FRED
- [ ] If the check finds at least one indicator with a genuinely new value, the affected parts of the page (table, countdown, AI section) update in place, and the AI interpretation is re-run and shown
- [ ] If the check finds nothing new, the page is left exactly as it was — no re-render, and **no AI call is made**, since there's nothing new to interpret
- [ ] A check that finds new data writes it back to the shared historical data store (the same store the v1 email pipeline reads/writes), so the page and email stay consistent
- [ ] If the background check fails outright (source API down, rate-limited, timeout, etc.), the page simply stays on the last stored data — same visible outcome as "checked, found nothing new"
- [ ] The fallback/initial state includes the last successful AI summary/directional read, not just the indicator table — this requires persisting the most recent AI response (text + directional read + generated-at timestamp) to the data store, since v1 never saved it (v1 generated it fresh per email and discarded it after sending)
- [ ] ~~The page shows a visible freshness label/timestamp~~ — dropped; found distracting in practice, and the background check's in-place content updates (see the "checking for updates" indicator below) are enough signal on their own
- [ ] While the background check is in flight, the page shows a visible "checking for updates" indicator, so the reader isn't left wondering whether anything is happening; it disappears once the check settles, regardless of whether it found new data, found nothing new, or failed

## Epic: Ticker Dashboard

### Story 2 — Ticker Watchlist Configuration
**As** the investor, **I want** to maintain my ticker watchlist — and the groups it's organized into — in a simple config file, **so that** I can add, remove, or regroup tickers without touching application code.

**Acceptance Criteria**
- [ ] Tickers are defined in a local JSON config file (per Section 7 of the requirements doc), grouped under group names that are themselves defined by the file — not a fixed list of categories hardcoded in the app
- [ ] Initial watchlist matches the config draft: SPY, IVW, DGRO (stocks); VGIT, VGLT (bonds); VIGI, VYMI, EMB (international); FTEC + other sector ETFs (sector); MSFT, RELY + other trusted individual stocks (individual)
- [ ] Adding or removing a ticker requires only editing the config file — no code change
- [ ] Adding, removing, or renaming an entire group requires only editing the config file — no code change (this is the key difference from a v1.1 draft that had group names fixed in code)
- [ ] An invalid or unrecognized ticker symbol in the config is skipped with a logged warning rather than breaking the whole dashboard

### Story 3 — Ticker Dashboard Page
**As** the investor, **I want** a web page showing my ticker watchlist grouped by asset type, **so that** I can review prices and trends across all my holdings in one place without logging into Fidelity.

**Acceptance Criteria**
- [ ] Page runs locally (e.g. `localhost`) — no public hosting, no domain, no login needed in this version (same hosting decision as the Indicator Digest Page, Story 1)
- [ ] Tickers are displayed grouped under headers matching the group names in the config file exactly — the page doesn't assume any fixed set of groups
- [ ] Each ticker card shows: current price, 52-week range, 20-day moving average, 200-day moving average, and recent related news
- [ ] Price and moving-average data is sourced from Finnhub (per Section 6 of the requirements doc); the free-tier ~20-minute delay is acceptable and does not need to be surfaced as an error state
- [ ] A ticker whose data fails to load (API error, rate limit) shows a visible per-card error state rather than breaking the rest of the dashboard
- [ ] Reloading the page re-fetches or re-reads current data rather than showing a stale snapshot from an earlier visit

---

## Cross-Cutting Non-Functional Criteria (apply to all stories above)
- [ ] Neither page requires user authentication
- [ ] Both pages are usable on a desktop/web browser (per the v1.1 device scope — no mobile app)
- [ ] A data-source outage (FRED, Finnhub) or missing data degrades gracefully (visible error/empty state) rather than crashing the page
