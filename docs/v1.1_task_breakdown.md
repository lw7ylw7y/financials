### Story 1 / 1a — Indicator Digest Page: Live Pull with Fallback

| Task | Estimate |
|---|---|
| 1.1 `live_pull.py` — split into `get_initial_page_data()` (stored-data-only, no network calls) and `check_for_updates()` (the actual live pull; gated so nothing new means no calendar refresh, no AI call, no save) (Section 4 of the tech design) | 3h |
| 1.2 Independent freshness per section: table/countdown can update from a check while the AI section is left on its last `last_ai_response` if only the Gemini call fails | 2h |
| 1.3 `page_template.py` — Indicator Digest Page rendering: AI section, table (grouped Leading/Coincident/Lagging, each row with an inline-SVG trend sparkline), countdown, disclaimer, a "Checking for updates..." indicator shown for the duration of the background check | 3h |
| 1.4 `/` + `/api/check` route wiring in `app.py` | 0.5h |
| 1.5 Tests (below) | 2.5h |
| **Subtotal** | **11h** |

**Tests**
- Initial `/` render is built entirely from stored data — never calls `run_ingestion`
- The background check finding at least one updated indicator refreshes the release calendar, re-runs the AI interpretation, and persists via `save_state()`
- The background check finding nothing new (or failing outright) reports no update — no calendar refresh, no AI call, no save — and the page is left exactly as rendered
- FRED succeeds but Gemini fails after retries → table/countdown content updates in place while the AI section keeps showing the last `last_ai_response` (independent freshness, per Section 4.1/4.3 of the tech design)
- Brand-new install (`last_ai_response` absent, no digest ever sent) renders a "no AI interpretation on file yet" placeholder without crashing
- AI content is labeled as informational commentary, not personalized financial advice (same guardrail as the email)
- Each table row renders a sparkline; a single-point history renders as a dot only, not a line
- The "Checking for updates" indicator is present on initial render and is cleared by the page's script once `/api/check` settles, whether or not anything updated

## Suggested Build Order
Dependency-driven:
1. Cross-Cutting Foundation (Flask scaffold — nothing else can be manually verified without it)
2. Extract `build_digest_content()` + persist `last_ai_response` (both epics' page depends on this; also the point where v1's shipped email code gets touched, so do it early and re-run v1's existing test suite before building on top of it)
3. Story 1/1a — Indicator Digest Page (reuses the most existing code, lowest new-integration risk)
4. Story 2 — Ticker Watchlist Configuration (config loader is a prerequisite for Story 3)
5. Story 3 — Ticker Dashboard Page (net-new integration — Finnhub — highest-risk item, left last so earlier stories aren't blocked on a new third-party API)
6. Cross-Cutting / Integration dry runs, once both pages exist
